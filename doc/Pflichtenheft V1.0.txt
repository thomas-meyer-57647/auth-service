Pflichtenheft – Auth Service
Pflichtenheft V1.0

Service-Name: 	auth-service
Version: 	1.0
Stand: 	18.02.2026
Geltungsbereich: 	Microservice zur Authentifizierung und Session-Verwaltung 	innerhalb eines Multi-Mandanten-Portals (je Tenant/Company), 	inkl. Registrierung/Onboarding (Tenant-Bootstrap), E-Mail-	Verifikation, verpflichtender MFA (TOTP), Social Login, JWT Issuer 	(JWKS), Refresh-Sessions (24h oder 3 Monate), Logout sowie 	Recovery (Passwort & MFA).
1. Einleitung
1.1 Ziel
Ziel ist die Bereitstellung eines zentralen Auth-Services, der:
Benutzer-Authentifizierung (Login) für ein Portal ermöglicht
Registrierung/Onboarding inkl. Tenant-Erstanlage (Bootstrap) abbildet
E-Mail-Verifikation erzwingt (vor Aktivierung)
verpflichtende MFA über TOTP erzwingt (vor Aktivierung und bei Login)
Social Login ermöglicht (z. B. Google/Facebook)
JWT Access Tokens ausstellt (mit tenant_id und Multi-Audience aud) und Public Keys als JWKS veröffentlicht
Refresh-Sessions verwaltet (Session-Policy 24h oder 3 Monate)
Logout (nur aktuelle Session) unterstützt
Recovery-Prozesse für Passwort und MFA anbietet (Recovery via E-Mail/SMS)

1.2 Abgrenzung / Nicht-Ziele (MVP)
Nicht Bestandteil des MVP:
Vollständiges Berechtigungsmodell (RBAC/Permissions) ? IAM-Service ist Quelle der Wahrheit
Benutzerprofile/Stammdatenverwaltung ? User-Service
Verwaltung von Unternehmen/Standorten als fachliche Masterdaten ? Company-Service
Template-Verwaltung/Rendering ? Template-Service
Zustellung von E-Mails/SMS/WhatsApp inkl. Retry/Provider-Handling ? Messaging-Service/Delivery-Service
Globale Token-Blacklist in allen Services (“Logout überall sofort”) im MVP (stattdessen: Refresh-Revocation + kurze Access Tokens)
1.3 Begriffe
Tenant/Company: Mandant im Portal; Isolation über tenant_id.
PENDING: Vorläufiger Zustand während der Registrierung (noch nicht aktiv).
ACTIVE: Aktivierter Zustand; Nutzer darf produktiv arbeiten.
Access Token (JWT): kurzlebiges Token für API-Calls (immer mit exp).
Refresh Session: serverseitig verwaltete Session, steuert “24h vs 3 Monate”.
MFA (TOTP): Time-based One-Time Password (Authenticator-App).
Recovery: Wiederherstellung bei Verlust von Passwort oder MFA-Device.

Korrelation (correlationId)
4. Fachliche Anforderungen
4.1 Mandantenmodell / Tenant-Bootstrap (MUSS)
Benutzer erstellt Tenant aktiv im Registrierungsprozess (Firma/Unternehmen + Standort).
Der erste registrierte Benutzer eines neuen Tenants wird automatisch Tenant-Admin.
Weitere Benutzer dürfen nur durch den Tenant-Admin des jeweiligen Tenants hinzugefügt/eingeladen werden.
4.2 Registrierung / Onboarding (MUSS)
4.2.1 Ablauf (MUSS)
1. Registration Start
Anlage PENDING-User (Auth + User-Service)
Anlage PENDING-Tenant/Company und PENDING-Standort/Location (Company-Service) als „Dummy“
Versand E-Mail-Verifikation (Messaging/Template/Delivery)
2. E-Mail-Verifikation
Nutzer bestätigt Verifikationslink (Token)
3. MFA Enrollment (TOTP)
Nutzer richtet TOTP ein (QR/Secret, Code-Bestätigung)
4. Aktivierung
User wird ACTIVE
Company/Location werden ACTIVE (Dummy wird “scharf geschaltet”)
IAM: Tenant-Admin Zuweisung + Standardrollen/Permissions werden final gesetzt
4.2.2 Zeitfenster / Cleanup (MUSS)
Registrierung muss innerhalb von 24 Stunden abgeschlossen werden.
Wird die Registrierung nicht innerhalb von 24h abgeschlossen, werden PENDING-Daten gelöscht:
User (inkl. Credentials/Identities, MFA PENDING, Tokens)
Tenant/Company (Dummy)
Standort/Location (Dummy)

4.3 E-Mail-Verifikation (MUSS)
Verifikation erfolgt über einen zeitlich begrenzten Token (max. 24h im Registrierungsprozess).
Token wird serverseitig nur gehasht gespeichert.
Resend ist möglich, aber rate-limitiert.
4.4 MFA (TOTP) (MUSS)
MFA ist verpflichtend.
Ohne erfolgreiches MFA Enrollment darf kein User ACTIVE werden.
Login erfordert nach Primary Auth immer eine MFA-Prüfung (TOTP).
4.4.1 Backup/Recovery (SOLL)
Backup-Codes SOLL (einmalige Anzeige, nur Hash speichern).
4.5 Login (MUSS)
4.5.1 Login-Methoden (MUSS)
Passwort-Login (E-Mail + Passwort)
Social Login (Google/Facebook u. a.)
4.5.2 Login-Flow (MUSS)
1. Primary Auth (Passwort oder Social)
2. MFA Challenge (TOTP)
3. Session anlegen (Refresh Session) entsprechend Session-Policy
4. Access Token ausstellen
4.6 Session-Policy (MUSS)
Beim Login kann der User wählen:
24 Stunden Session
3 Monate Session
Technische Umsetzung:
Access Token ist kurzlebig (immer exp gesetzt)
Refresh Session bestimmt die Gesamtdauer (24h oder 3 Monate)
4.7 Logout (MUSS)
Logout beendet nur die aktuelle Session (Refresh Session).
Keine globale Abmeldung über alle Geräte im MVP.
4.8 Passwort-Reset (MUSS)
4.8.1 “Passwort vergessen” (MUSS)
Reset wird über E-Mail (oder optional SMS) gestartet.
Response ist neutral (“Falls Konto existiert …”), um Enumeration zu vermeiden.
Reset Token:
kurz gültig (10–30 Min)
gehasht gespeichert
one-time use
4.8.2 Passwort ändern (eingeloggt) (SOLL)
Step-Up MFA (TOTP) erforderlich.
Nach Passwortänderung: Sessions widerrufen.
4.9 MFA Recovery (MUSS)
Recovery via E-Mail/SMS als “Rescue”, nicht als regulärer 2. Faktor.
Nach erfolgreicher Recovery:
alte MFA Konfiguration invalidieren
neues MFA Enrollment erzwingen
Sessions widerrufen

5. JWT / Token-Contract (MUSS)
5.1 Access Token – Header (SOLL)
alg: RS256 (oder ES256)
kid: Key-ID (für Rotation)
typ: JWT

5.2 Access Token – Claims (MUSS)
Pflicht:
iss (String)
sub (String, userId)
aud (Array, Multi-Audience)
iat (Number)
exp (Number) immer gesetzt
jti (String)
tenant_id (String)
Scopes:
scp (Array) und/oder scope (String)
Empfehlung: scp ist führend, scope optional.
5.3 Access Token – Claims (SOLL)
sid (Session-ID)
amr (Array, enthält "totp")
auth_time (Number)
subject_type = "USER"
5.4 Audience (aud) – Multi-Audience (MUSS)
aud enthält u. a.:
iam-service
user-service
template-service
company-service
5.5 Tenant-Regel (MUSS)
tenant_id ist Quelle der Wahrheit. Wenn Request zusätzlich Tenant-Angaben enthält (Header/Path/Query), muss dieser Tenant dem Token-tenant_id entsprechen, sonst Zugriff verweigern.

5.6 Service Tokens (SOLL)
Für interne Calls (Auth ? Template/Messaging/Delivery) kann Auth kurzlebige Service Tokens ausstellen:
subject_type = "SERVICE"
sub = "auth-service"
aud enthält Zielservice
tenant_id gesetzt (wenn Zielservice Tenant-Kontext erzwingt)
exp kurz (2–5 Minuten)
scp minimal

8. Sicherheit / Nicht-funktionale Anforderungen
8.1 Passwort-Sicherheit (MUSS)
Hashing BCrypt/Argon2
keine Klartext-Secrets in Logs
Passwort-Policy (SOLL): Mindestlänge etc.
8.2 Rate Limiting / Abuse Schutz (MUSS)
Login Brute-Force Schutz
Registrierung, Resend, Password Reset, MFA Recovery jeweils rate-limitiert
8.3 Token-Transport (SOLL)
Access Token via Bearer Header
Refresh Token als HttpOnly Secure Cookie (Web)
CSRF Schutz über SameSite/CSRF Token/Origin Checks
8.4 Observability (SOLL)
correlationId Logging
Actuator health/metrics

9. Sonderfälle & Ausnahmefälle (MUSS)
Folgende Sonderfälle sind umzusetzen und zu dokumentieren (Verhalten, Fehlercodes, Logging/Audit, Retry/Compensation):
Resend Verifikation (Mail nicht angekommen) + Rate Limit + neutrale Antwort
Registrierung erneut starten nach Ablauf (24h) + vollständiges Cleanup
Idempotency/Doppelklick/Retry bei kritischen POST-Endpunkten
Race Conditions zwischen Cleanup und Verifikationsabschluss (atomare Statuswechsel)
Duplikat E-Mail (ACTIVE User) – keine neue Tenant-Erstellung
TenantKey Kollisionen
Teilfehler in verteilten Abläufen (User/Company/IAM/Messaging/Delivery) inkl. Kompensation
Provider-Sonderfälle (Social Provider ohne verifizierte E-Mail, E-Mail geändert, Provider down)
Account Linking Regeln (Passwort/Google/Facebook)
Clock Skew Toleranz (iat/exp)
Key Rotation/JWKS Caching (mehrere aktive Keys)
Refresh Token Theft/Reuse (Rotation/Reuse-Detection)
Statusänderungen während Session (User/Tenant disabled) – spätestens bei Refresh prüfen
Password Reset als Umgehung für MFA: Reset ändert Passwort, setzt MFA nicht zurück
MFA Enrollment Abbruch/Fortsetzen bis 24h
MFA Recovery Missbrauch (Cooldown/Rate Limit/Notifications)
E-Mail Änderung (falls unterstützt): Re-Verify + Konflikte
Delivery/Template Fehler (Template missing/render fail, Bounce, Delivery down): Retry/Status

11. Abnahmekriterien (Auszug)
MUSS:
Registrierung erstellt PENDING User + PENDING Tenant/Location und triggert Verifikationsmail (Auth?Messaging?Template?Delivery).
Aktivierung nur nach E-Mail-Verifikation + TOTP Enrollment.
Cleanup nach 24h löscht PENDING-Daten zuverlässig.
Login ist immer 2-stufig (Primary + TOTP).
Session-Policy 24h und 3 Monate funktionieren via Refresh Session.
Logout beendet nur die aktuelle Session.
JWT Contract eingehalten (iss/sub/aud/iat/exp/jti/tenant_id + scopes; Multi-aud).
JWKS liefert Public Keys inkl. kid; Services können validieren.
Sonderfälle umgesetzt (Idempotency, Teilfehler, Reuse-Detection, Rate Limits).
SOLL:
Password Change mit Step-Up MFA.
Backup Codes.
Monitoring/Actuator.
